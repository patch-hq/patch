# Wire Protocol

Event-based WebSocket protocol between server, hosts, and surfaces. Built on the [`happy-wire`](https://github.com/slopus/happy/tree/main/packages/happy-wire) package structure with patch-specific events.

## Goals

- One message = one discrete event. Surfaces render a stream of events.
- Every logged chat event has a `seq` per chat, numbered by the chat's host. A reader holds a position and continues from it (§ Chat history).
- No request/response. Both sides push events; correlation via `id` fields where needed.

## Idempotency

`chat.input` carries a client-generated `localId` (UUID). The host enforces uniqueness per `(chatId, localId)`, and so does the server for the messages it holds (`01-server.md` § Responsibilities) — a duplicate post (retry on flaky network, surface reconnects mid-send) is dropped without creating a duplicate user message. Agent-emitted events (`chat.message`, `chat.tool_call` etc.) are emitted exactly once by the host and carry no `localId`.

### Host outbox (host ↔ server)

Everything a host sends that the server records goes through one outbox per host: every logged chat event, `chat.spawned`, `chat.state` and `host.account`. A host says `outbox: true` in its `hello`, and the server answers `hostOutbox: true` in `auth.ok`. A server that keeps the whole record also answers `recordComplete: true`; a host sends turn boundaries and `nativeRef` only to such a server, and keeps them in its outbox for one either way. A server that keeps each entry's branch answers `recordBranches: true`; a host sends `branchId` on entries and sends a side branch's entries only to such a server, and runs the one-time record import only for one. A server that answers `patch_peek` and `patch_history` from its record and keeps the account's tool log answers `serverReads: true`; a host sends `patch.tool_log.entry` only to such a server (an older one keeps no tool log, and the calls made meanwhile are not recorded) and refuses those two tools with an "update the server" error on one without it.

| Type                     | Direction     | Payload                                                                                                                                                                                               |
| ------------------------ | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `host.outbox`            | host → server | `{position, event}` — `event` is the frame being recorded; `position` is its outbox position, numbered across the whole host and never reused                                                         |
| `host.outbox_ack`        | server → host | `{through}` — every position up to `through` is committed; the host may forget them. Sent shortly after commits, one per burst                                                                        |
| `host.record_import`     | host → server | `{chatId, events[], done}` — one frame of a chat's whole record for the one-time import (`01-server.md` § Record import). Taken in without broadcasting; `done` marks the chat's last frame           |
| `host.record_import_ack` | server → host | `{chatId}` — the record holds everything the import sent for this chat                                                                                                                                |
| `patch.tool_log.entry`   | host → server | `{entry: {ts, tool, callerChatId?, targetChatId?, durationMs, ok, err?}}` — one cross-chat tool call the host ran, for the account's tool log (`01-server.md` § Responsibilities). Belongs to no chat |

The host keeps every event on disk until it is acknowledged, so a host restart loses nothing. After a reconnect it resends everything after the last `through` it received, in order, before anything new; a position the server already holds is acknowledged again and not applied twice. Live-only frames (text deltas, `chat.queued`, presence, answers to requests) are sent as themselves and bypass the outbox; a transcript event sent bare is refused. There is no per-chat comparison between host and server, the server never asks a host for history, and a host never answers a surface's history request (`01-server.md` § Host outbox; host side: `02-host.md` § Host outbox).

### Chat history (surface ↔ server)

Only the server answers. Positions are a chat's `seq` values and are exclusive in both directions.

| Type                   | Direction        | Payload                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chat.history_request` | surface → server | `{requestId, chatId, branchId?, after?, before?, limit?}` — at most one of `after` and `before`. `after`: entries with `seq > after`, oldest first. `before`: the `limit` entries immediately before `seq = before`. Neither: the chat's last `limit` entries, its last screen. `limit` is 1–500, default 100. `branchId` names a branch's own track (`04-chats-and-folders.md` § Parallel branches), a side thread's included; absent means the active branch. Only the server answers, from its record, whether or not the chat's host is online; no request for history ever reaches a host, and the server sends the chat's `chat.branches` after the page |
| `chat.history`         | server → surface | `{requestId, chatId, branchId?, entries[], more, through, pending[], queued[]}` — `entries` in seq order; `more` says entries remain in the direction asked; `through` is the chat's latest `seq` on the server; `pending[]` is every question still unresolved on the chat, whatever range was asked, so a surface can always answer it; `queued[]` is the chat's waiting messages (`04-chats-and-folders.md` § Message queueing)                                                                                                                                                                                                                             |

The host sends every tool result whole. A result over 4 KB reaches surfaces, in history and live, as a reference carrying its size and a short preview; the reader expanding it fetches the body (`01-server.md` § Responsibilities).

Live entries and history are one stream. A surface receives a followed or focused chat's entries as they commit, merges them with history answers by `seq` and drops duplicates by `seq`. Reconnecting continues from the highest `seq` the surface holds; it never starts a chat over. Opening a chat the device holds asks for entries `after` that position; opening one it does not hold asks for the last screen and pages older with `before` as the reader scrolls up.

### Account feed (surface ↔ server)

One ordered feed per account tells every device what changed anywhere: chat list entries, statuses, and new entries for the chats the device follows. Every list-level frame the server sends to surfaces (`chat.spawned`, `chat.state`) carries `feedPos`, numbered across the account. `chat.state` is the chat's whole list entry: its status, its background task, subagent and pending-wake counts, and the rest of what a list row shows.

| Type          | Direction        | Payload                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `feed.resume` | surface → server | `{after?, follow[]}` — sent after `hello` on every connect. `after` is the last `feedPos` the device holds, absent when it holds none; `follow[]` is `{chatId, after, branchId?}` for each chat in the device's copy (`05-surfaces.md` § Loading). The server sends the latest list-level frame for every chat changed after `after`, one per chat, then each followed chat's entries after its `after` with every question still unresolved on it (as `pending[]` on `chat.history`, `requestId: "feed"`, `more` running forwards), then live frames. ### Host health

A host reports how its machine is coping with every heartbeat: `host.health` `{hostId, memTotalBytes?, memAvailableBytes?, swapTotalBytes?, swapUsedBytes?, load1, cpuCount, eventLoopLagMs, intervalMs, topProcesses}`, every 15 s. Memory and swap are reported on Linux only; a platform that cannot measure a thing leaves it out. `topProcesses` (up to five groups of look-alike processes with their combined memory) is filled only while memory is short. The server consumes it and never relays it.

The server uses the reports only to explain a host dropping off: a host that cannot be reached at all is `host.offline`, whose frame carries a `reason` worked out from the host's last heartbeat: `asleep` (the host's machine reported going to sleep, via `machineHostId` on the desktop app's `surface.input`, after that heartbeat) or `unresponsive`. A host that is merely busy or slow is not announced: there is no banner, notification or condition event for it.

While memory is critical (under 4% available, or low with swap at least 90% used), the host itself holds new turns: they are queued (`chat.queued`) and run in order when memory recovers.

### Answering with content (`approve_with_edits`)

Most permissions are a yes or a no, and `approve` / `deny` carry everything the
host needs. Some are not: the user's answer IS content, and it has to travel
back into the tool call before it runs. `approve_with_edits` is that channel —
one string, `editedNewString`, which the host substitutes into the pending
tool's arguments per tool before granting permission. Where it lands depends on
the tool: `Edit.new_string`, `Write.content`, `NotebookEdit.new_source` (the
Monaco-edited file content — `14-design-web.md` § Diff editor), and
`AskUserQuestion.answers` (the user's chosen options, JSON-encoded — see below).
A decision of `approve_with_edits` naming a tool with no such argument is an
error, not a plain approval: the host denies the call and says so with a
`chat.error` (`invalid_frame`), because approving a tool whose answer was
dropped is exactly the silent-empty-answer failure this channel exists to fix.

Required means present and a string, not non-empty. The empty string is a
meaningful answer for the file-edit tools — it is how an edit that deletes the
content is approved — so a surface sends it through unchanged rather than
refusing it or downgrading to a plain `approve`. A missing or null
`editedNewString` is still an error, since that is an answer that was lost
rather than an answer of nothing.

`AskUserQuestion`'s answers are `{[questionText]: selectedOptionLabel}` — a
multi-select joins its labels with `, ` into that one string — JSON-encoded into
`editedNewString`.

### Files (surface ↔ host)

Backing the editor rail's file browser (`14-design-web.md` § File browser). Paths resolve on the chat's own host, inside the chat's folder.

| Type                     | Direction      | Payload                                                                                                                                                                                                    |
| ------------------------ | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `patch.files.request`    | surface → host | `{requestId, chatId, path, content?}` — list `path`'s entries, or read that one file when `content`                                                                                                        |
| `patch.files.response`   | host → surface | `{requestId, entries?, content?, error?}` — `entries[]` is `{name, kind}`; a missing file or a path escaping the chat folder errors                                                                        |
| `file.write`             | surface → host | The editor save, listed under Surface events above                                                                                                                                                         |
| `patch.file_op.request`  | surface → host | `{requestId, chatId, op, path, to?}` — `op` is `create` (empty file), `create_dir` (one directory), `delete` (one file or one EMPTY directory) or `rename` (to `to`, inside the same folder)               |
| `patch.file_op.response` | host → surface | `{requestId, ok, path?, error?}` — `path` is where it landed (`to` for a rename); `error.code` is one of `chat_not_found`, `path_escape`, `not_found`, `exists`, `not_empty`, `missing_target`, `internal` |

Unlike the listing above, these four change the disk, so the pair is a REQUEST/RESPONSE with an acknowledgement rather than a fire-and-forget surface event: the user is told the outcome, and "the frame went somewhere" is not an outcome. A host too old to know the type drops it, the server's wait times out and the surface reports a failure — an operation can never read as having succeeded because nobody answered.

Nothing here overwrites and nothing recurses. `create` and `rename` refuse an occupied destination (`exists`), `delete` refuses a directory with contents (`not_empty`), a destination's parent directory is never created implicitly (`not_found`), and neither the chat folder itself nor anything a symlink resolves to outside it is a legal target (`path_escape`). Refusals carry the host's own sentence, with host paths stripped — the surface is told the chat-relative path it asked about and nothing about the host's layout.

### Chat search (surface → server)

Backing `GET /api/chats/search?q=&limit=&offset=` (`04-chats-and-folders.md` § Search), answered by the server from its own record of every chat, whatever state the hosts are in. ### Cross-chat tools

`patch_send_to`, `patch_stop` and `patch_spawn` act on a chat's host. One whose target is on the calling chat's own host is short-circuited in-process; one naming another host goes over these frames, relayed by the server to that host. Surfaces see them either way, so cross-chat activity renders as an audit trail.

`patch_spawn` names its host directly (`hostId` on the frame), since the caller is choosing a host to create a chat on. `patch_send_to` and `patch_stop` take only a `targetChatId` — the caller learns which chats exist from `patch_list_chats`, not which host each is on — so the server resolves the owning host from its chat index and relays there. `patch_peek` and `patch_history` read the chat's record: the calling host sends them to the server, which answers from its record whichever host owns the chat and whether it is online (`01-server.md` § Responsibilities, Search).

A `patch_send_to`, `patch_stop` or `patch_spawn` naming an offline host, or a `targetChatId` the server has no record of, returns an error to the calling agent, naming the problem, within the turn. A tool result is part of a turn in progress, so it resolves rather than being held the way `chat.input` is, and the agent decides what to do about the host being down.

The same holds for a host that is ONLINE and REFUSES: a cross-host call is answered by the named/owning host with its own `.response`, and the calling agent's tool call resolves on that answer — the real result, or that host's own error. A refusal reaching only the target's log would leave the agent believing a call that never landed had succeeded.

A `patch.peek.request` or `patch.history.request` always carries `requestId`, and the server answers it with `patch.peek.response` / `patch.history.response` itself; it never relays one to a host. (A frame without one is an older host's audit record of a read it did itself, and is not answered.) A send, stop or spawn frame carries `requestId` only when it is a genuine cross-host relay the caller is waiting on; the same frame with no `requestId` is a same-host call already resolved in-process, kept on the wire purely as an audit record, and the server never relays it.

### Audio relay over the host link (server ↔ host)

Backs `07-voice-app.md` § Voice is a per-host capability's tunnelled path —
the DEFAULT way `/audio/:sessionId` reaches a voice session on a host that
has not declared a direct `audioRelayHost` (which is every host except one
co-located with the server, unless an operator has set one explicitly). A
host is never itself internet-reachable (`01-server.md` § Responsibilities, WebSocket hub —
it only dials out), so instead of the server dialling in, every frame of the
session is carried over the SAME outbound link the host already holds,
multiplexed by `sessionId`. The host bridges those frames to its own LOCAL
audio WSS (`ws://127.0.0.1:<audioPort>/audio/:sessionId`) exactly as a
co-located surface would reach it directly, so the host's audio server cannot
tell a tunnelled connection from a direct one.

Shaped like the terminal streams (open/frame/close over a persistent,
server-relayed correlator) with one addition: `frame.binary` marks whether
the inner WS frame it carries was text or binary, because a voice session's
inner stream mixes BOTH (JSON control frames and raw PCM16) on one socket,
unlike a byte-opaque stream. `open` travels server →
host only; `ready` is informational (the server does not wait for it —
frames sent before the host's local bridge is open are queued there, same
discipline as the direct-dial path's own queue-until-open); `frame` and
`close` travel in either direction; `error` travels host → server only, and
the server turns it into the surface-facing `audio.error {code:
'host_unreachable'}` — NO FALLBACK to any other pipeline.

| Type                      | Payload                                                                                         |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| `patch.audio_relay.open`  | `{sessionId}` — server asks the host to bridge this session to its own local audio WSS          |
| `patch.audio_relay.ready` | `{sessionId}` — the host's local bridge socket is open (informational)                          |
| `patch.audio_relay.frame` | `{sessionId, data, binary}` — one inner WS frame's bytes, base64, in either direction           |
| `patch.audio_relay.close` | `{sessionId}` — either side ending the bridge cleanly                                           |
| `patch.audio_relay.error` | `{sessionId, code, message}` — `code` is `connect_failed` (the host's own local connect failed) |

### Composer drafts (surface ↔ server, server-owned)

The server owns unsent composer text for an existing chat directly — not the host, so a draft is available and syncs live even while the chat's host is asleep (`14-design-web.md` § Composer). ### Job-trigger events

No dedicated event type. When a job trigger (cron / webhook / Todoist) fires server-side, the server emits the action event directly — a `chat.spawn_request` or a `chat.input` (`08-triggers-and-jobs.md` § Action) — targeted at the host the action carries, identical to what a surface would emit. The host does not know or care whether the event came from a user or a fired trigger.

Job CRUD itself goes over HTTP to the server (see `01-server.md` endpoints), not over the WebSocket. The Manager / Speakers threads invoke `patch_job_*` tools that the host implements as HTTP calls to the server, authenticated with the host's `daemonKey`.

### Hooks (server ↔ host)

Backing `POST /api/hooks/check` (`20-hooks.md` § Checking a user*message). A
surface's check request is plain REST, never the socket — it is a
request/response, not a stream a reconnect needs to replay. The server
resolves which hooks match, then sends one `hook.check_request` per matching
hook to the chat's own host, all fired together, each with its own
`requestId` and the hook's own `timeoutMs`; a host that doesn't answer in time
is that run's own timeout (`20-hooks.md` § Outcome), not a dropped frame.
Hook CRUD is REST only, exactly like jobs (`03-wire-protocol.md` §
Job-trigger events): `patch_hook*_`cross-chat tools are HTTP calls the
host makes to the server with its`daemonKey`, same as `patch*job*_`.

An `agent_response` check (`20-hooks.md` § Checking an agent_response) has no
surface asking it, so the HOST starts it: one
`hook.agent_response_check_request` per settled turn, carrying the agent's
full reply and a deterministic tool-call tally it already has without a
round trip. The server resolves matching `agent_response` hooks and
dispatches each with the SAME `hook.check_request` / `hook.check_result` pair
the `user_message` path uses — `reply` standing in for `message`,
`toolCallsSummary` riding in `context` — then reports every result back in
one `hook.agent_response_outcome`, unaggregated: the host decides what a
block/advise/failure means for the chat, not the server. `checkId` is
minted by the host and echoed back so a stale answer (a slow round-trip
a newer turn has already superseded) is recognisable and ignored.

| ----------------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `hook.check_result`                 | host → server | `{requestId, hookId, status: 'ok'\|'failed'\|'timeout', decision?: 'pass'\|'advise'\|'block', analysis?, suggestion?, error?, durationMs}` — `decision` present only when `status` is `'ok'` |
| `hook.agent_response_check_request` | host → server | `{hostId, chatId, checkId, folder, specialThread, reply, toolCallsSummary}`                                                                                                                  |

## Forward compatibility

Host names. A host is a `host`: the id is `hostId`, its lifecycle events are `host.online`, `host.offline`, `host.unauthenticated`, `host.host` and `host.account`, and a host's `hello` carries `clientType: 'host'`. A peer that sends the daemon names (`daemonId`, `daemonVersion`, `daemon.*`, `clientType: 'daemon'`) has them rewritten by both decoders to the host names before validation (`canonicalizeHostNames`), and everything the server, host and surfaces send uses the host names. REST bodies and query strings get the same rewrite on the server.

Patch ships as independently-deployable layers down unrelated delivery
paths (`11-deployment.md` § Version reporting), so at any moment some reader is older than its
sender: a phone that was off during the deploy, a desktop shell that has not
restarted, a host that OTAs on its own schedule. The rule for what a
reader does about that is:

Strict at ingress. Tolerant, and narrowly so, at every reader that can be
older than its sender.

| Reader                          | Decoder        | Why                                                                                                                                                                                                                                       |
| ------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server ← surface, server ← host | `decode`       | The server is the protocol's referee, and is never older than anything talking to it: every client artifact is published by the deploy that ships the server. An unknown key arriving here is a typo, not the future, and has to be loud. |
| Web surface, mobile surface     | `decodeCompat` | Routinely older than the host whose frames they render.                                                                                                                                                                                   |
| Host ← server                   | `decodeCompat` | Hosts OTA on their own schedule and routinely lag the server.                                                                                                                                                                             |

`decodeCompat` tolerates exactly two things, both of which mean "my sender is
newer than me", and nothing else:

1. An unknown field on a known event. The key is stripped and the frame is
   re-validated in full. If it does not then pass on its own terms, it is
   refused exactly as before.
2. An unknown event type. The frame is dropped quietly and counted. There is
   nothing a build can do with an event it has never heard of, and a banner per
   frame is worse than nothing.

Everything else — a missing required field, a wrong type, a bad enum, invalid
JSON — still throws `WireDecodeError` and still reaches the user as an error.
So does a frame that carries an unknown key and a real error: forward
compatibility is not cover for a bug.

This is not a fallback, which the principles forbid (`principles.md`). A
fallback invents a value the sender did not send. This discards a value the
reader cannot use, and says so: both kinds are counted per process
(`wireCompatStats()`) and reported by the connection diagnostics screen
(`12-error-and-offline.md` § Connection diagnostics screen). A tolerated FIELD
is drift, reported and passing. A dropped event TYPE is a build missing
behaviour its agent already has, so it FAILS the check and tells the user to
update that surface — which is the "update me" an explicit protocol-version
handshake would have bought, without a second thing to keep in step.

Why not strict everywhere plus a version handshake. A handshake tells a
stale surface it is stale; it does not let it keep working, and refusing the
whole session over one added field is a worse outage than the field. It also
needs a number bumped by hand on every change — a thing to forget — where this
needs nothing.

What it does NOT license. A field may be added; a field may not change
meaning, and a required field may not be removed or narrowed. Tolerance is for
additions only — an older reader ignoring an addition still renders something
true, where a reader given a re-used field renders something false. A breaking
change is still a breaking change, and needs a new event type.

Adding a VALUE to an existing enum is still breaking, and deliberately so.
An unknown key can be ignored and leave the frame true; an unknown enum value
cannot — a new `chat.dequeued.reason` an older surface has never heard of has no
honest rendering, and picking a near neighbour would be the fallback the
principles forbid. So `decodeCompat` refuses it, loudly, like any other invalid
value. Carry the new state as a new optional field instead, or design the field
open from the start and make every reader handle "something I don't know" as a
rendered state of its own.

## Meeting events

Surface → host (relayed by the server; each adds the chat to the surface's watched set): `meeting.control_request {chatId, action: start|pause|resume|end|tune|name_voice, settings?: {clipSeconds, analyseSeconds}}` (`settings` with `start` and `tune`), `meeting.get_request {chatId}`, `meeting.audio {chatId, source: mic|system, audioBase64, speakerName?}` (16 kHz mono PCM16 WAV), `meeting.action_request {chatId, actionId, decision: do|chat|dismiss|done|reopen}` (`do` runs an agent action and `chat` starts the user's own in a new chat linked to the meeting's; someone else's action takes neither; `done` ticks one off and `reopen` unticks it), `meeting.action_request {chatId, actionId, owner}` (reassign someone else's action to a speaker or `Everyone`), `meeting.action_request {chatId, actionId, assign: {kind, owner?}}` (hand it to the user, the agent, or someone else), `meeting.action_request {chatId, actionId, title}` (rewrite it), `meeting.action_request {chatId, add: {title, kind, owner?}}` (a new action of the user's writing), and `meeting.action_request {chatId, agentRuns: false}` (agent actions never start by themselves, so `true` is refused). Exactly one of these per request. Each action in `MeetingState.actions` has a `kind` of `mine|other|agent`, an `owner` for `other`, a `chatId` once its chat exists, and a status of `pending|running|done|dismissed`.
The agent feed adds `meeting.research_request {chatId, on}` (the "Agent researches during call" switch; turning it on researches from that moment, not the past). `MeetingState` carries `cards` (research cards: `kind` explained|fact|answer, `title`, `at`, 1–3 `bullets`, and for a fact check a `verdict` correct|off|unclear; a card with a figure in its bullets, or a Correct/Off verdict, must carry an http(s) `source {name,url}`), `researchOn`, `researchError` and `agentEdits` (what the chat agent changed in the notes, with wall-clock `at` and a chip `label`). Transcript lines may carry `name` (the participant the call app lit up, from `speakerName`). Host → surfaces: `meeting.state {chatId, meeting: MeetingState | null}`, the whole state each time (including `live`, the provisional unanalysed transcript, and `settings`); detail-level, so only surfaces watching the chat receive it. A refused request comes back as `chat.error`. See `14-design-web.md` § Meeting mode.
