# Server

One Node/Fastify process. The server is a role, not a machine: it runs on its own always-on box, or on a user's Mac as a background service of its own (`11-deployment.md` § Server on a Mac). It uses no external database, so it stays light enough to run on a Mac. Deployed on a box with a public address and HTTPS, it is the only component that needs to be internet-reachable. A server without such an address is reached through a relay instead (`10-auth.md` § Relay).

## Responsibilities

- Account + host registry. User has one account (Ed25519 `publicKey`). Each host registers separately (`daemonKey`) via QR-code linking, and the registry holds a record per host: `hostId`, host name, platform, version, and last-seen state. Hosts are peers, and any number of them may be registered.
- WebSocket hub. Persistent connections from surfaces and every host; server routes events by `(account, chat)`, and a chat's `hostId` selects the host a surface event is delivered to. Hosts dial out to the server and hold the connection.
- Chat index. The server keeps an index of every chat in the account — name, host, folder, job, user flags (snoozed, archived, pinned), status, last activity and the rest of what a chat list row shows — built from the chat record, what hosts report and what users do, and saved in the account's folder as it changes. The chat list and its sections are pages of it (`GET /api/chats`), and a restart begins from it. Anything that reads a chat's activity — the job concurrency gate (`08-triggers-and-jobs.md` § Concurrency), the sweep, the completion push — reads the index. It is saved to `/data/chat-index.jsonl`, append-only: a change adds one line per chat that changed (its whole row, or a removal), so a change costs the size of a row however many chats the account has, and the latest line for a chat is the chat. A line torn by a crash is skipped when it is the last one; damage anywhere else is logged and the server starts empty. At each start, and when superseded lines pass two per chat plus a thousand, the file is rewritten as one line per chat. An account that still has `/data/chat-registry.json` from before has it imported at the first start and deleted at the first write.
- Chat→host binding. A chat lives on one host for its whole life; the server records which host and routes that chat's events to it alone (`04-chats-and-folders.md`). Only replacing a host rebinds chats (`11-deployment.md` § Replacing a host); moving a chat to another host starts a new linked chat there (`04-chats-and-folders.md` § Moving to another host).
- Cross-host relay. A cross-chat tool call that acts on a chat on another host (send, stop, spawn) arrives from one host and is delivered to that chat's host, with the response relayed back to the caller (`03-wire-protocol.md` § Cross-chat tools). Cross-chat reads are answered by the server itself (Search, below). A call for an offline host is answered with an error naming it rather than buffered, since the caller is waiting inside a turn.
- Relay presence. With `PATCH_RELAY_URL` set it holds its relay channel and ends devices' encrypted sessions on its own loopback address (`10-auth.md` § Relay); `GET /api/relay` reports whether it is reachable that way.
- Chat record. The server holds Patch's record of every chat: one append-only log per chat (`/data/chat-logs/<chatId>.jsonl`), in Patch's format, and the only source for display, search, paging and every surface (what an entry holds, including the provider's `nativeRef`: `04-chats-and-folders.md` § History). A chat has exactly one writer, its host, which numbers the chat's entries (`seq`); the server stores them in that order and never renumbers. A host taking over a chat (replacing a host, a Manager home change) continues from the server's high-water mark for it. A resend of an entry the server holds is dropped without being broadcast again; a different entry at a `seq` already held is refused and logged, never broadcast. Each entry's `nativeRef` is kept with it and not relayed to surfaces. Turn boundaries (a turn started; a turn ended with its outcome) are kept beside the entries by turn id: each is placed at the chat's highest `seq` when it happened and takes no `seq` of its own, so it never collides with an entry. The host sends every tool result whole. The server keeps a result over 4 KB as a body stored once under `/data/chat-logs/blobs`, referenced from the log by `{$blob, bytes, mime, preview}`; history and live frames carry the reference, and the body is served by `GET /api/chats/:chatId/blob/:sha` when the reader expands the row (`03-wire-protocol.md` § Chat history). Live streaming (text deltas, tool progress) is not part of the record and never waits on a write. Search reads the record too: earlier servers kept a second copy of message text under `/data/chat-mirror` for it, and that folder is removed on the first start without it.
- History reads. Surfaces read only from the server; opening a chat never waits on its host. A surface asks for what is new since a position and for older pages before one, and live events and history are one stream, so a reconnecting surface continues from its position (`03-wire-protocol.md` § Chat history). The HTTP history route takes the same `after` and `before` positions. A chat opens on its last screen and older entries are paged in as the reader scrolls up; a large tool result's body is fetched only when expanded.
- Account update feed. One feed per account tells each device what changed anywhere: chat index entries, statuses, and new entries for the chats that device follows (`03-wire-protocol.md` § Account feed). A device resumes the feed from its own position, so its local copy (`05-surfaces.md` § Loading) catches up without reloading.
- Chat status. The server alone decides each chat's status. Hosts report facts — turn started, turn ended with its outcome, question pending or answered — the server's own links say whether a host is connected, restarting or gone, and accounts report their state (`10-auth.md` § Account states); from these the server derives one status per chat and enforces the allowed transitions (`12-error-and-offline.md` § Chat status lists both). A host going silent mid-turn makes the chat host offline, never a stale running or a false failed. The status travels on the index entry and the feed; surfaces display it and never derive it.
- Search. Every chat is searched on the server, from its record and the index, whether its host is online or not (`04-chats-and-folders.md` § Search). The cross-chat reads agents make — `patch_list_chats`, `patch_search_chats`, `patch_peek`, `patch_history`, `patch_activity` — are answered by the server the same way, never by asking hosts (`06-threads-manager-speakers.md` § Cross-chat toolset).
- Server-run queue. The server holds the messages behind a running turn for a host that can take them and decides when each goes in (`04-chats-and-folders.md` § Message queueing). It records the host the user chose to run the Manager and carries out a change of it as a handover; it never moves the Manager by itself (`06-threads-manager-speakers.md` § Changing home).
- Held messages. A message to a chat whose host is offline is held by the server in `/data/held-input.json`, shown in the chat as queued for that host, and delivered when the host returns, so a surface can always send. A message held for seven days expires undelivered and is said in its chat, never dropped silently (`12-error-and-offline.md` § Guaranteed input delivery). A host removed from the account loses what was held for it; a host replaced by another hands what was held to its replacement.
- Waiting messages. The server keeps each chat's queue from `chat.queued` and `chat.dequeued` and sends the waiting messages with the chat's history (`04-chats-and-folders.md` § Message queueing).
- Push fanout. Expo's push API for Android push. Push tokens registered per surface. Android only.
- Webhook ingress. `POST /api/webhooks/:jobId`. Payload matched against the job's JSONata filter; action dispatched to the host the action names. Todoist instead uses one shared `POST /api/webhooks/todoist` that fans an event out to every todoist-trigger job whose filter passes, since a Todoist app has a single callback URL (`08-triggers-and-jobs.md` § Todoist).
- Cron scheduler. Server runs an in-process scheduler that fires `cron`-trigger jobs at their next match, evaluating each expression in the trigger's own timezone. Each tick produces a payload (`{ firedAt }`) and dispatches the job's action to the host that action names, same as a webhook trigger. See `08-triggers-and-jobs.md`.
- Broadcast log. Every notify passes through the server, so it is the server that records one against the mediating thread when the channel is `speakers`, and serves those records to the Manager host when the user replies on that channel (`09-notifications.md` § Broadcast context).
- Presence tracker. Every connected surface heartbeats (`ping` every 10s, timeout at 30s). Drives notification routing (see `09-notifications.md`). Host presence is tracked per host.
- Host build distribution. Serves the current host artifact per OS/arch and its version manifest, which back host self-update and the install command a surface offers for a new host (`02-host.md` § Runtime and installation).
- Job definitions. Stores job JSON files (`/data/jobs/*.json`), watches for changes, notifies the host.
- Manager sweep gate. Watches every chat on every host for the conditions that make a sweep due (`06-threads-manager-speakers.md` § The sweep), and asks the Manager host to run one when they are. It belongs here because it is the only component with the cross-host view; it decides nothing beyond when a sweep is due and which chats are candidates — the decision and the actions are the Manager host's.
- Thread rotator. Checks, on a steady tick, whether it's a special thread's scheduled rotation time (`06-threads-manager-speakers.md` § Session rotation); when it is, asks its host to rotate it (`chat.rotate_request`). The host owns the actual session swap and digest; the server owns only the clock, same split as the sweep gate.
- Settings. The source of truth for every setting that is not tied to one host, including backend accounts and provider keys (§ Settings).
- Composer drafts. One unsent-composer-text entry per existing chat, owned by the server rather than the host so it is available even while a chat's host is asleep (`14-design-web.md` § Composer, `03-wire-protocol.md` § Composer drafts) — stored in `/data/composer-drafts.json`. Carries the draft's attachments too (§ Draft attachments below) — text and attachments are independent axes of the same entry, so an entry exists while EITHER has something, not only while there's typed text.
- New-chat drafts. Not-yet-spawned new chats — id, folder, host, model and text — owned by the server the same way, so the same Drafts list shows live on every surface (`14-design-web.md` § New chat drafts, `03-wire-protocol.md` § New-chat drafts) — stored in `/data/new-chat-drafts.json`. Same attachments/text independence as composer drafts.
- Draft attachments. A file attached to either draft kind above uploads to the server IMMEDIATELY — before the message is sent — rather than waiting for Send to trigger the upload (`14-design-web.md` & `15-design-mobile.md` § Composer → Attachments). Two storage roots, because a composer draft's chat already exists and a new-chat draft's doesn't:
  - Composer draft (existing chat): reuses the ordinary per-chat attachment storage (`/data/attachments/<chatId>/<id>` — same as a sent message's) and the SAME host hand-off (`patch.attachment.store_request`/`_response`) an ordinary send-time upload already used — the chat's host session already exists, so there's nowhere else useful for the bytes to sit in the meantime. For a chat whose host is offline the server keeps its copy and makes the hand-off when the host returns, before any held message that names the attachment is delivered. The upload (`POST /api/chats/:chatId/attachment`) additionally registers the resulting ref onto that chat's composer draft, which is what fans the chip out to every other surface (`composer_draft.attachments_changed`). Removing a chip before Send (`DELETE /api/chats/:chatId/attachment/:id`, only permitted while the id is still in that draft — a sent message's attachment is never reachable through it) deletes both copies: the server's serving copy and the host's, via a `patch.attachment.delete_request`/`_response` host RPC pair mirroring the store one. Sending detaches the draft's current attachments from its bookkeeping WITHOUT deleting anything (`POST /api/chats/:chatId/attachments/detach`) — the files now belong to the sent message, which references the exact same ids.
  - New-chat draft: no chat exists yet, and the host's own store call requires one, so this is SERVER-ONLY storage at attach time — `/data/new-chat-draft-attachments/<draftId>/<id>`, no host round trip. `POST /api/new-chat-drafts/:draftId/attachment` stores the bytes and registers the ref on the draft (`new_chat_draft.attachments_changed`); `GET .../attachment/:id` serves it back (unauthenticated, unguessable id, same reasoning as the per-chat serve route); `DELETE .../attachment/:id` removes it, no host involved. The ONE host hand-off happens at `POST /api/new-chat-drafts/:draftId/promote` (body `{chatId}`), called once the draft is promoted to a real chat on first send: it MOVES (not copies) every attachment the draft still holds into the chat's ordinary per-chat storage, keeping the same id, and does the host store round-trip for each — the client never re-uploads a byte for this hop.
  - Cleanup. Discarding a draft outright (an explicit discard, or a bare `composer_draft.clear`/`new_chat_draft.discard` arriving with attachments still on it — defensive; the ordinary per-chip DELETE route already frees each one before an entry can go fully empty) frees every attachment it still holds — server bytes and, for a composer draft, the host's copy too. Deleting a chat frees its composer draft's still-unset attachments the same way (never-sent, so never part of the chat's real history). Nothing is ever left orphaned on disk.

Agent sessions, LLM calls and voice processing (Whisper + Kokoro for phone, web, and standalone-device surfaces) belong to the host; a chat's provider session stays on its host in the provider's own format and the server never reads it (`02-host.md`, `04-chats-and-folders.md`).

## Host outbox

Each host sends what is new through one outbox, numbered host-wide (`02-host.md` § Host outbox, frames in `03-wire-protocol.md` § Host outbox). The server commits each event durably — fsynced into the chat's log, or into the index or held state it belongs to — before broadcasting it, then acknowledges the outbox position. Writes to a chat's log are fsynced once per acknowledgement, just before it is sent; a write that failed leaves nothing in memory the disk lacks, no acknowledgement goes, and the server drops the host's link so it resends. After a reconnect the host resends everything after the last acknowledgement. A transcript event a host sends outside its outbox is refused, and a host whose `hello` lacks `outbox: true` is logged as having nothing recorded until it updates. There is no per-chat comparison: the server never asks a host for history, and a host never answers a surface's history request.

## Record import

A host that held chats before the server's record kept everything sends each of them once (frames in `03-wire-protocol.md` § Host outbox), to a server that answers `recordImport: true` and `recordComplete: true`. Every chat the host holds goes, including chats the server has never seen, and all of each: every entry whole (tool results with their bodies) with its `nativeRef`, every turn boundary, and every question that was answered or ran out. The server keeps each entry by its `seq`, so an entry it already holds is not stored twice and gains a `nativeRef` it lacked; nothing is broadcast. One chat at a time, each acknowledged before the next. The host marks a chat done only on the acknowledgement, and the import complete once every chat is done, so an interrupted import carries on at the next connect and a chat that could not be read is tried again there. Its progress is versioned: a host whose earlier, partial import (which sent only what the record then lacked) completed runs this one once more over every chat, then stops. Chats begun after it are recorded live through the outbox.

## Settings

The server holds the account's settings and every host runs from the copy the server last sent it. A host never changes a shared setting itself. The same holds with one host or many: a single-host install runs the server and its host side by side.

Shared by every host, stored on the server:

- Provider accounts: every provider's credentials, signed in once and available on every host, their order and each provider's account strategy (`10-auth.md` § Backend credentials). They are encrypted at rest and handed to hosts over the host link.
- Provider keys (`02-host.md` § Provider keys). Saving one makes a free read-only request to its provider and answers with the verdict (working and what it powers, limited, rejected, or provider unreachable); saved keys are rechecked at start and hourly, and a key the provider has since refused is flagged in Settings. The key is saved whatever the verdict. Verdicts are held in memory, not stored.
- Two host behaviours that were environment variables are settings: `smallJobModels`, the ordered model list for small one-shot jobs (`02-host.md` § Small jobs), and `speechBackend`, the speech-to-text engine (`02-host.md` § Speech set-up). The server refuses an empty or repeated model list and a `speechBackend` that is not `auto`, `off`, `groq`, `elevenlabs`, `local` or `parakeet`. `toolPromptOverrides` is the third such setting (`06-threads-manager-speakers.md` § Tool prompts). No host reads any of the three from its environment (`principles.md` § Configuration).
- Agent behaviour: default model, default permission mode, the limit behaviour (`10-auth.md` § Limits), automatic continue (`12-error-and-offline.md` § Continue), question expiry, chat-name interval, and the layers in `14-design-web.md` § Agent behavior.
- Experimental features: one on/off switch, off by default, that shows or hides the half-finished features (`14-design-web.md` § `/settings` details → Experimental features). Account-wide, so every surface agrees.
- Voice: the Kokoro voice and the voice config matrix (`07-voice-app.md`).
- The Manager's home host, the Manager sweep and quiet hours, the voice address word, and the special threads' model and rotation schedule.
- `Send to my phone after`: how long a computer may sit idle before notifications go to the phone instead (`09-notifications.md` § Presence heuristic). 1 minute (the default), 5 minutes, or `Only when I lock`.

Held by each host, because they describe that host: its name, its project folders, its installed components and self-update, and Claude Code memory (stored under that host's project paths). Which providers and models a host can run is reported by that host.

Settings are stored in `/data/settings.json`. Credentials and provider keys are stored in `/data/secrets.json`, encrypted at rest with `/data/secrets.key`, which the server makes (0600) the first time it starts with no secrets file; there is nothing to configure. The key keeps the secrets out of anything that copies `secrets.json` on its own; it is no protection against someone who can read all of `/data`. If the secrets cannot be read — the key is missing, is not a key, or does not decrypt the file — the server still starts: it sends hosts no settings (a snapshot without the accounts would sign them out), refuses every change to an account or key with 503 `secrets_unreadable`, and puts the reason and the fix on `settings.changed.problem`, which Settings shows at the top of every page. A secret goes out only to hosts, over their host link. A surface only ever sees where a secret came from and its last four characters, and nothing logs a value.

Every change goes through the server: a surface over REST, the CLI through the server, an agent through the `patch` tools. The server validates it, commits it, and sends every connected host a `settings.snapshot` carrying a version. A host also receives the snapshot whenever it connects, so a host that was offline is current as soon as it is back. The host writes the snapshot to `~/.patch/settings.json` (mode 0600, atomic), applies it, and answers `settings.applied` with the version, or with the reason it could not apply it. Settings shows any host that is behind or refused, by name. While the server is unreachable a host keeps running on its last snapshot, and a settings change made on that host is refused, naming the server, rather than applied locally.

A host that connects for the first time since settings were shared is asked, once, for everything it held on its own — its accounts, its provider keys and, for the first host only, its settings — before it is sent a snapshot. Accounts already held are not added twice: a second copy of the same Claude organisation or the same OpenAI login is dropped, and a label that would read twice gains the host's name. A host whose import fails keeps running on what it held and is asked again when it next connects.

Some values start on a host and still end on the server. Provider refresh tokens stay on the server, which renews them serially and sends only access credentials to hosts (`10-auth.md` § Backend credentials). A successful sign-in on one host replaces the shared login for that credit source. A value found on the host — the backend's own login, or a provider key in the host's environment — can be adopted from Settings, which asks that host to send it to the server as the shared value.

## Starting with no settings

A server starts with nothing configured. It listens on port 3970 and keeps its state in the data folder (§ Data folder), `~/.patch-server/data` (`$PATCH_SERVER_HOME/data` when that is set), made on the spot. The first time it starts it makes what it needs in that directory, 0600: `secrets.key` (§ Settings) and `internal.token`, the voice-session secret each host is handed when it is registered (`10-auth.md` § Host registration). `PATCH_DATA_DIR` and `PATCH_INTERNAL_TOKEN` override them. A value that is set and unusable (a data directory that does not exist, a token under 16 characters) stops the server rather than being quietly replaced, and so does a token file that holds no token.

## Data folder

Everything the server keeps is in one self-contained folder: settings, secrets and `secrets.key`, the registry, every chat's record and blobs, the chat index, held and queued messages, drafts and their attachments, jobs and their logs, pads, artifacts and the broadcast log. Nothing it needs lives outside it, so moving the server to another machine is carrying that folder across (`11-deployment.md` § Moving the server). Each account's data is kept apart on disk, in its own folder inside it; a `/data/...` path in this spec names a place inside the data folder, within the owning account's folder for anything that belongs to an account.

## Stack

- Node 20+, TypeScript.
- Fastify for HTTP + WebSocket.
- Flat files and append-only logs in the data folder (§ Data folder); no external database.
- Commit before broadcast. Server only emits over WebSocket, and only acknowledges a host's outbox, after the underlying write is fsync'd. Otherwise a crash mid-write leaves clients seeing state that was never persisted.
- `ws` for WebSocket; protocol defined in `03-wire-protocol.md`.
- No E2E encryption to server (we own it and the host). TLS termination only.
